# Intro to Feature Engineering

So far in our preprocessing journey, we have learned how to clean data (removing missing values) and scale data (Standardization).

But what if the data is clean, but it's still not in a format the model can learn from? Or what if there is a hidden pattern that the model is struggling to see? We have to use **Feature Engineering**.

## 1. What is Feature Engineering?

Feature Engineering is the creation of brand new columns (features) based on the information hiding in your existing columns.

It highlights a few key rules about this process:

*   **The Goal:** To improve model performance and expose insight into relationships between features.
*   **The Catch:** You cannot automate this easily. It requires you (the human) to use your own brain and domain knowledge to understand the dataset first. What works for a medical dataset won't work for a financial dataset; it is highly dataset-dependent!

## 2. Common Feature Engineering Scenarios

Here are four classic scenarios where raw data is useless to a machine learning model until you engineer it.

### Scenario A: Text Data (NLP)

**The Raw Data:** Look at the table below. It has raw sentences like "Feature engineering is fun!"

| Id | Text |
|---|---|
| 1 | "Feature engineering is fun!" |
| 2 | "Feature engineering is a lot of work." |
| 3 | "I don't mind feature engineering." |

*   **The Problem:** A machine learning algorithm is just a calculator. It cannot read English.
*   **The Engineering:** We have to use Natural Language Processing (NLP) to count the words and convert that sentence into a vector (a list of numbers) that the computer can do math on.

### Scenario B: Categorical Strings

**The Raw Data:** Look at the table below. We have a column for `fav_color` with values like blue, green, and orange.

| user | fav_color |
|---|---|
| 1 | blue |
| 2 | green |
| 3 | orange |

*   **The Problem:** Again, the computer can't do math on the word "blue".
*   **The Engineering:** We must encode this text into numbers. (We learned how to do this previously using Dummy Variables / One-Hot Encoding, turning those colors into binary 1s and 0s!).

### Scenario C: Dates and Timestamps

**The Raw Data:** Look at the table below. We have full date strings like July 30 2011.

| Id | Date |
|---|---|
| 4 | July 30 2011 |
| 5 | January 29 2011 |
| 6 | February 05 2011 |

*   **The Problem:** A computer doesn't know that "July" comes after "June". Also, a highly specific timestamp (down to the exact second) is usually way too granular and will just cause the model to overfit.
*   **The Engineering:** We can extract specific, useful pieces of time! We can break that one column into three brand new columns: Month (7), Day (30), and Year (2011). Or, we could even engineer a binary column: `is_Weekend` (1 or 0).

### Scenario D: Aggregating Lists of Numbers

**The Raw Data:** Look at the table below. We have three separate test scores: `test1` (90.5), `test2` (89.6), and `test3` (91.4).

| user | test1 | test2 | test3 |
|---|---|---|---|
| 1 | 90.5 | 89.6 | 91.4 |
| 2 | 65.5 | 70.6 | 67.3 |
| 3 | 78.1 | 80.7 | 81.8 |

*   **The Problem:** Feeding all three of these highly correlated scores to a model might be redundant and overly complex.
*   **The Engineering:** We can mathematically combine them! We can create a brand new column called `average_test_score` that perfectly captures the student's overall performance, allowing us to drop the original three columns and make our model much simpler and faster.
