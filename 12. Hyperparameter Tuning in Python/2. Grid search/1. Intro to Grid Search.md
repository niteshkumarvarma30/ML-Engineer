# Intro to Grid Search

In our previous lesson, we used a single Python `for` loop to automate testing a single hyperparameter (like the number of neighbors in KNN).

But advanced algorithms (like Gradient Boosting Machines - GBM) have dozens of hyperparameters. What happens when you want to tune 2, 3, or 4 of them at the exact same time?

## 1. The Problem: The Nested Loop Nightmare

*(Look at your Automating 2 Hyperparameters screenshots).*

If you want to test 3 different `learning_rate` values and 4 different `max_depth` values, you could write a Nested Loop (a loop inside a loop).

```python
results_list = []

# Loop 1: Go through the learning rates
for learn_rate in learn_rate_list:
    # Loop 2: Go through the max depths
    for max_depth in max_depth_list:
        
        # Build, train, and score the model
        results = gbm_grid_search(learn_rate, max_depth)
        results_list.append(results)
```

This works perfectly for 2 hyperparameters. But *(Look at your From 2 to N hyperparameters screenshot)*:
If you want to test 4 hyperparameters, you have to write 4 nested loops. The code becomes a massive, unreadable staircase. It is highly inefficient to write code this way!

## 2. The Danger: Exponential Math

*(Look at your How many models? screenshot).*

When you add new hyperparameters to test, the number of models you have to build does not grow in a straight line. It grows exponentially.

*   If you test 5 values for Hyperparameter 1, and 10 values for Hyperparameter 2, the computer has to run $5 \times 10 = \mathbf{50 \text{ models}}$.
*   What if you add 10-Fold Cross-Validation to make sure the scores are accurate? Now the computer has to run $50 \times 10 = \mathbf{500 \text{ models}}$.
*   Add a 3rd hyperparameter with 5 options? Now you are running **2,500 models**.

## 3. The Solution: Visualizing a "Grid"

*(Look at the Introducing Grid Search screenshots).*

Instead of writing messy nested loops, data scientists visualize this problem as a literal Grid.

Down the left side (Rows), you list all the `max_depth` values you want to test (e.g., 4, 6, 8).
Across the top (Columns), you list all the `learn_rate` values (e.g., 0.001, 0.01, 0.05).

| `max_depth` \ `learn_rate` | 0.001 | 0.01 | 0.05 |
| :--- | :--- | :--- | :--- |
| **4** | (4, 0.001) | (4, 0.01) | (4, 0.05) |
| **6** | (6, 0.001) | (6, 0.01) | (6, 0.05) |
| **8** | (8, 0.001) | (8, 0.01) | (8, 0.05) |

**How it works:** Every single intersecting cell on this grid represents exactly *one unique model recipe*! For example, the top-left cell creates a model exactly like this:
`GradientBoostingClassifier(max_depth=4, learning_rate=0.001)`

Running a model for every single cell in this hyperparameter matrix is known as a **Grid Search**.

## 4. Grid Search: Pros and Cons

Is Grid Search the ultimate tool? Yes and no. Here is the final breakdown from the transcript.

### ✅ The Pros

*   **It is Programmatic:** It saves you from writing massive, 4-level nested `for` loops.
*   **Guaranteed Best Result:** Because it exhaustively tests every single cell in the grid, it is 100% mathematically guaranteed to find the absolute best combination (out of the options you provided).
*   **Easy to Explain:** The concept of a visual grid is very easy to explain to non-technical business stakeholders.

### ❌ The Cons

*   **Computationally Expensive:** As we saw with the exponential math, adding just a few more parameters can cause the grid to explode into millions of combinations, taking days to run.
*   **It is "Uninformed":** Grid Search is blind. It doesn't learn from its mistakes. If a `max_depth` of 4 gets a terrible score, a human would know to stop testing 4. Grid Search doesn't know; it stubbornly keeps testing every other combination with a depth of 4 anyway!

*(Later in the course, we will learn about "informed" methods that actually learn as they go!)*
